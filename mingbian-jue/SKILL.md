# 明辨诀 v3.0.2 — 第一性原理审查模式

## 这是谁
这技能是干嘛的：用 6+1 步法审查一个方案/决策/事故的完整流程，确保事实准确、假设不飘。
谁写的：科技虾（周星星）· 拍板人：錡哥

## 30 秒开始
1. 有人（錡哥/AI）提出"审查 X"
2. 从"/scrutiny"开始，走完 6+1 步
3. 第 6 步"实态核验"别跳——这是最容易出错的地方

## 什么时候别用
- 只是查个信息/看条消息时不用
- 已经拍板执行的事不用再审
- 5 分钟能解决的小问题不用

> **6+1 步法**：6 步审查 + 第 6 步「实态核验」+ 6.5 子步「系统环境核验」。
> **倒逼来源（原环境教训）**：3 次自审连错（只信项目自述未核验实际）+ 磁盘方案改 ulimit 被系统服务绕过 0% 生效。
> **拍板人**：錡哥 · **作者**：周星星 🌟

> ⚠️ **核心警告 1：项目自述 ≠ 实际**——不核验就动手 = 必定失误
> ⚠️ **核心警告 2：改配置 ≠ 自动生效**——改系统级配置（如资源限制/内核参数/系统服务/定时任务）前，必查是否有底层服务在接管，导致改了不生效（详见第 6.5 步，Linux 服务场景为主）

## 触发词

- `/scrutiny`（显式调用）
- 用户说"审计"、"审查一下"、"复盘"、"review 一下这个方案"、"帮我审审"

> **何时不应启动**：见上方「什么时候别用」。原环境中系统级判定放在 `AGENTS.md`；WorkBuddy 对应工作区约定（如 SOUL.md / 项目上下文），此处不重复。

## 核心指令

> **不要急着动手，通过第一性原理，采用 Pre-Mortem + 否定性对抗 + 追问性对抗，全面审查一遍。**

## 审查流程（6 步法 · 含第 0 步 Pre-Mortem）

### ⚡ 轻量模式 / 快速审查

如果审查对象明显简单（单文件审阅、配置检查、bug 复现），跳过事实收集和推荐行动，只做：
- 否定性对抗（质疑假设）
- 追问性对抗（验证结论）
- 一句话根因

**自动判断规则**：审查对象 < 3 个变量 或 < 5 条可分离事实 → 自动降级轻量模式。

### 第 0 步：Pre-Mortem（项目启动前必做 · critical）

> **借鉴**：Gary Klein 2007 HBR "Performing a Project Premortem" + Mitchell/Russo/Pennington 1989 Prospective Hindsight
> **作用**：在审查开始**前**想象"项目已经失败" → 倒推所有可能的失败原因

```
## Pre-Mortem 输出格式
**假设失败时点**：项目已上线 6 个月
**想象失败情境**：xxx 已彻底失败
**倒推失败原因**（5-10 条）：
  1. xxx
  2. xxx
  ...
**高风险信号**（标红·列入 critical 必查项）：
  - xxx
**已预防措施**：xxx
```

**为什么有效**：利用"prospective hindsight"认知现象，把未来视角变成当下分析，**风险识别率提升 30%**。

### 🚨 触发 /scrutiny 的强制场景（v3.0.1 补 · 7-13 P0 触发 · inc-006）

> **铁律 M 落地版**：以下操作即使**看起来原子且可逆**，也必须先 /scrutiny，不能以"五行诀刚审过"为由跳过。

| 操作类型 | 失误风险 | 反例教训 |
|---------|---------|---------|
| `ln -s` / 硬链接 | 跳过审查直动手、引用断 | 7-9 08:32 P22 软链（inc-006 触发） |
| `mv` / `cp` 到 bind-mount | 路径重写 → cron / script 引用全断 | 同上 auth.json 迁移 |
| `cron jobs.json` 字段改动 | 静默失败 34h+ 不报 | 6-29 dict 损坏 |
| 共享 skill 路径挪动 | 多 agent 引用断 | 7-7 skill-move 教训 |
| `docker-compose` / 配置文件改 | 全局影响 | 7-12 cron payload |
| "原子且可逆" 类心智 | **任何心智判定都需走 /scrutiny** | 7-9 根因深层 |

**核心警示**：**五行诀 ≠ /scrutiny**（前者思维框架，后者操作流程，两者正交不可替代）。

### 第 1 步：事实收集

列出所有已确认的客观事实（facts），每一条都必须有来源佐证：
- 日志原文 / 配置文件原文 / 工具输出 / 运行结果
- 标记每条事实的**确信度**（高/中/低）

### 第 2 步：否定性对抗（5 假设 + 5 追问）

对**每一个假说、推断、假设**执行否定性质问。

#### 5 种假设分类（先归类，再对抗）

| 类型 | 描述 | 追问方向 |
|------|------|---------|
| **Consensus** | 共识/大家公认 | "谁说的？为什么信？有没有反例？" |
| **Hidden** | 隐藏在语言/默认设置里 | "不写出来会怎样？假设合理吗？" |
| **Authority** | 因为权威信了 | "源头还成立吗？权威本身有没有错？" |
| **Temporal** | 过去对、假设现在还对 | "时点变了没？环境变了没？" |
| **Correlation** | 共存就当成因果 | "相关 = 因果？有没有第三变量？" |

#### 5 个否定问题

- "如果这个假设是错的，现象会是什么样？"
- "有没有其他解释能同时解释所有事实？"
- "有没有更简单的解释？"
- "这个结论隐含了什么前置条件？这个条件成立吗？"
- "如果把这个原因去掉，现象是否还存在？"

#### 3 档结论分类（v1.0 已有 · v2.0 保留）

| 标记 | 含义 | 处理 |
|------|------|------|
| ✅ **Survives** | 经受住所有对抗测试，可信 | 写入最终结论 |
| ⚠️ **Conditional** | 某些条件下成立，需标注条件 | 写入时附带前提 |
| ❌ **Fails** | 被否定证据击破，放弃 | 写入"已排除的假说" |

### 第 3 步：追问性对抗 + 绿黄红风险等级（v2.0 新加）

对**每一个看似成立的结论**追问：
- "这个结论有直接证据吗？还是推断出来的？"
- "证据链是否完整？有没有跳过的步骤？"
- "有没有考虑过时间线？先发生和晚发生的有因果关系吗？"
- "是不是把相关性和因果性搞混了？"
- "是不是看到相似时间戳就归类为同一原因？"
- "有没有更精确的说法？"

#### 绿黄红风险等级打分（v2.0 新加 · 与 3 档结论分类**共存**）

| 等级 | 颜色 | 含义 | 处理建议 |
|------|------|------|---------|
| 🟢 | **绿** | 低风险 | 可继续推进 |
| 🟡 | **黄** | 中风险 | 建议增加防御措施后再推进 |
| 🔴 | **红** | 高风险 | **停止推进**，必须先解决 |

**与 3 档结论分类的关系**：
- 3 档分类（Survives/Conditional/Fails）= **结论可信度**（逻辑层）
- 绿黄红 = **风险严重度**（业务层）
- 两者可独立评估：一个 Conditional 结论可能是 🟢 低风险（条件可控）；一个 Survives 结论可能是 🔴 高风险（幸存但仍危险）

### 第 3.5 步：反方视角

对当前最确信的结论，自问：
- "如果我是另一个 AI，看到同样的事实，会得出什么不同结论？"
- "我是不是选择性关注了支持我的证据？有没有被我忽略的反例？"
- "这个结论太漂亮了，是不是太漂亮了？"

### 第 6 步：实态核验（v3.0 新增 · **必走**）

> **背景**：3 次自审连错的教训（原环境沉淀，新环境教训写入 `.workbuddy/memory/lessons-learned/scrutiny/`）
> **5 次失误 100% 失效率** = 全因"只信项目自述，未核验实际"

#### 4 个硬命令（**审前必跑** · 跨平台）

> WorkBuddy 在 Windows 上走 Git Bash，下列命令可直接用；PowerShell 等价写法见注释。

```bash
find <项目> -type f | wc -l              # 1. 文件数 — 防"README 说待写，实际已写"
ls -la <项目>/                            # 2. 隐藏文件 — 防"判断空目录误删"
stat -c '%Y %n' <项目>/* | sort -rn | head   # 3. 时序 — 防"以为停更，实际正常间隔"
python -c "import json,sys; print(list(json.load(open(sys.argv[1])).keys()))" <file>  # 4. 字段位置
```

> PowerShell 等价：`(Get-ChildItem <项目> -Recurse -File).Count` / `Get-ChildItem -Force` / `Get-ChildItem | Sort LastWriteTime -Desc` / `(Get-Content <file> | ConvertFrom-Json).PSObject.Properties.Name`。

| 自述 vs 实际 | 行动 |

| 🟡 部分不符 | 标红，优先核验后再动 |

#### 6.5 子步骤：环境核验（**改配置类必走**）

> **核心警示（普适）**：**改配置 ≠ 自动生效**——一定要问「有没有更底层的东西在接管我这个配置，让它悄悄不生效？」审方案 = 审方案 + 审运行环境。
> **原始教训**：某磁盘方案改 `ulimit -c 0` 禁用 core dump，但系统装了 ABRT，内核把 core dump 直接 pipe 给 abrt-hook，**完全绕过 ulimit**——方案 0% 生效却毫无报错。这是最隐蔽的一类失误。

**核验通式（3 问 · 任何平台任何配置都适用）**：

1. **谁在我上面？** 这个配置之上有没有更高优先级的层会覆盖它？（构建工具覆盖源码配置 / 环境变量覆盖配置文件 / 系统服务覆盖用户设置）
2. **改了真生效吗？** 不能只看「配置文件改了」，要看「运行时实际值变了」——重新读一次实际生效值。
3. **能真触发一次吗？** 造一个最小场景把改动真跑一遍，确认行为按预期变化。

**WorkBuddy 常见场景对照（前端 / 应用开发为主）**：

| 改动类型 | 底层接管者（易被忽略）| 核验方式 |
|---------|---------------------|---------|
| 改 `.env` / 环境变量 | 构建时内联、`import.meta.env` 前缀规则、shell 已缓存旧值 | 重启 dev server + 打印实际读到的值 |
| 改 vite/webpack 配置 | 缓存(`node_modules/.vite`)、mode 覆盖、CI 另一套配置 | 清缓存重构 + 看产物 |
| 改 `package.json` 依赖版本 | lockfile 锁死实际版本 | `npm ls <pkg>` 看实际安装版本 |
| 改 Windows 系统设置 | 组策略 / 服务 / 注册表更高优先级 | 改后重新读取实际值 |

**Linux 服务器场景参考（仅当审的是 Linux 部署 / 运维方案时才用）**：

```bash
# core dump 接管者 / 审计服务 / 自动 bug 报告 / 定时任务覆盖 / 日志配额
cat /proc/sys/kernel/core_pattern        # | 开头 = pipe 给其他服务（绕过 ulimit）
systemctl status auditd --no-pager       # 审计服务是否拦截
systemctl list-timers --no-pager | head  # systemd-timer 是否覆盖 cron
prlimit | grep CORE; ulimit -c           # 改后看"实际生效"，不只看配置
```

## 质量标准

1. **每个假设可证伪** — "如果 X 错，会是 Y 现象"
2. **每个结论有证据** — "X 说"必须指明谁说、什么时候、为什么信
3. **至少 1 个非显然洞察** — 如果只是确认常识，再深挖
4. **反方不是为反而反** — 既然常识是真的就直说
5. **不确定 ≠ 假** — "没法证明真的"和"是假的"是两件事
6. **承认认知边界** — 哪些问题工具/视野够不到，明确说出

## 规则

1. **不急着动手** — 审查阶段不产生任何写操作
2. **不在证据不足时下结论** — 标记为"待验证"
3. **承认错误推断** — 明确说"我之前的推断错了"
4. **输出精简** — 只报需要使用者知道的内容
5. **先否定再肯定** — 默认假设"现在的一切推断可能都错了"
