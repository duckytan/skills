## 🎛 工作流执行机制选择（v3.1.2 新增 · 錡哥 23:45 拍板 + 00:50 仔细检查 + 01:02 WorkBuddy 实战反馈）

主控根据 stakes 自动选择执行机制,两套机制共存 + 完整兑底。子 agent 隔离是**编排层问题**，不修改三个依赖诀的方法论。

### 机制 A · 串行模拟（轻量 · 默认）

- **做什么**:主控 1 个进程,自己切 3 次视角,自己读 3 个 SKILL.md
- **适合**:日常 / 简化 / 默认模式
- **成本**:1x token
- **优势**:快 / 简单 / 共享背景天然
- **劣势**:context 污染风险（后司被前司带偏）

### 机制 B · sub-agent 隔离（重型 · 圆桌/重大决策）

- **做什么**:spawn 3 个独立 sub-agent,各自读自己的 SKILL.md 跑审查
- **适合**:圆桌模式 + 重大决策
- **成本**:~1.4x token（只圆桌时烧）
- **优势**:物理隔离防 context 污染 / 真印证
- **劣势**:token 略高 / 共享背景需显式传
- **避免剧透**：子 agent prompt 只说「调用 Skill 按 SKILL.md 执行」，不提前剧透结构（錡哥 WorkBuddy R1 实测反馈）

### 机制 C · 共享背景协议（防盲化 · v3.1 P0 · 錡哥 23:37 反馈 + WorkBuddy B 坑）

> **盲化风险**:隔离顺带把共享背景也切断——三司看不到同一份事实,各自盲点不同。
> **解法**:阶段 0 主控做客观事实收集,sub-agent 启动时显式传。

#### 阶段 0 · 事实收集（主控做 · v3.1 P0）

- **做什么**:客观陈述可核验的信息（数据/日志/配置原文/用户原话）
- **不做什么**:不下结论、不评对错、不替三司想答案
- **产出**:`memory/sanshi-tasks/<task-id>.md` 接力棒 + 一段「事实表」
- **🆕 外部事实表（v3.3）**:审查对象含「方案/项目/战略/选型」时，阶段 0 补调知彼诀产出「前置情报包」（知己内部事实 + 知彼外部候选 + 对标差距），作为事实表的外部参照部分——让三司不只基于内部事实审（闭门造车盲区）。

#### 事实表模板

```markdown
## 事实表（主控阶段 0 收集 · 仅客观信息）

### 数据/事实
- [可信源]:[原文/数据] — [采集时间]
- 例:cron logs:「17:00 health-check 失败」 — 7-25 00:30

### 用户原话
- 錡哥 7-25 00:30:「升级 sub-agent 模式」

### 排除项（不算事实）
- 不含"我觉得" / "可能" / "应该"
- 不含三司各自的判断

#### 阶段 0 留白条款（v4.2 新增 · 治「三司退化成复核员」）
> 事实表越满，三司越只做「验证 + 分级」，独立发现率越低。共享背景的目的是防盲化，不是替三司思考。

- **事实表上限 9 条**：超过即视为过载，须合并或下沉到 references
- **禁止倾向性标注**：主控不得在事实表中写入「疑似问题 / 这里可能有问题」等引导性判断
- **三司独立发现栏（强制）**：每司结论须含「主控事实表之外的发现」一栏，**允许为空但必须显式声明**「无独立发现」
- **边际发现率** = 独立发现数 / 总发现数，**< 20% 触发主控自检**（查是否阶段 0 喂太满）
```

#### sub-agent 接收协议

- 启动 task = 【事实表 + 任务摘要 + 该司专属指令】
- 不传主控的"判断" / "倾向"

### 机制 D · 失败兑底（v3.1 P0 · WorkBuddy C 坑补充）

> **为什么必要**:sub-agent 可能因网络/超时/token 爆等原因失败,主控必须有兑底。

#### 单 sub-agent 失败时

1. 主控检测 sessions_history 返回长度 < 100 字 = 失败信号
2. 自动重试 1 次（30 秒后）
3. 重试仍失败 → 主控降级到机制 A（主控代入该司视角跑审查）
4. 接力棒标黄「此司 sub-agent 失败,降级机制 A」

#### 2+ sub-agent 失败时

- 整个圆桌模式失败 → 升级錡哥，附「哪些司失败」+「主控推荐」

#### sub-agent 超时

- 默认 timeout = 15 分钟
- 超时后 kill → 同上失败处理

#### R1 实测先验（激活前必跑 · WorkBuddy 反馈）

- 在激活并行前跑一轮**只验证隔离可行性**的测试
- 起 3 个 `general-purpose` Agent，各 Skill 加载对应诀
- 检查：三司都能【Skill 加载】成功、各自独立 context、结论视角各异
- 结论：R1 通过 ✅ → 并行草案改「已启用」；R1 失败 → 暂不启用,保持串行

### 自动选择矩阵（v3.1.2 修订 · 与 v3.0 参与司规则联动）

| 任务 stakes | 触发判据 | 模式 | 执行机制 | 参与司 |
|------------|---------|------|---------|--------|
| 🟢 轻量 | 日常问答/单文件改 | 跳过 | 不跑 | — |
| 🟡 中低 | 单配置/单 bug | 简化 | 机制 A · 串行 | 仅明辨决 |
| 🟠 中 | 跨文件改/改配置 | 默认 | 机制 A · 串行 | 明辨决+破妄决 |
| 🔴 高 | 加铁律/跨边界/重大决策 | 圆桌 | 机制 B · sub-agent | 三司全跑 |
| ⚪ 錡哥指定 | 「会审」/「三司」/「圆桌」 | 按指定 | 按指定 | 按指定 |

#### 显式圆桌词不强制并行（v3.1.2 P0 · WorkBuddy B 坑）

⚠️ **「用户显式说圆桌」不单独强制并行**:
- 「三司会审审个配置修改」= 低 stakes 单模块 → 走 🟡 简化（串行）
- 「三司会审审加新铁律」= 高 stakes → 走 🔴 圆桌（并行）
- 措辞不强制 → **隔离信号组合判定**（改动范围 + stakes + 污染风险）

#### 事中升级并行（v3.1.2 P0 · WorkBuddy B 坑 · 「污染风险」是事中信号）

> 錡哥 23:37 反馈:污染风险是事中信号,不是开跑前输入。

机制：
1. 主控串行跑到一半,发现「后司被前司带偏」(如明辨决做完后,破妄决在结论里引用明辨决的根因)
2. 主控可触发「事中升级并行」：
   - 仅重跑被污染的后司(并行隔离下重跑单司安全,不污染其他司)
   - 不重跑前司(前司结论保留作为客观事实)
3. 接力棒标黄「事中升级 · 重跑 X 司」

### P0-P4 并行工作流（避免与主流程阶段 1-4 混淆 · WorkBuddy A 坑）

### 网状印证协议（sub-agent 之间 · v3.1 P1 · WorkBuddy D 坑补充）

> **注意**:并行下 6 方向是**主控读真实文本后的推测**，不是各司互评（三司互不可见）。

**主控驱动**（推荐,避免 sub-agent 互相干扰）:

```
for pair in [(A,B), (A,C), (B,A), (B,C), (C,A), (C,B)]:
    sessions_send(
        sessionKey=<被印证司的 session>,
        message=f"朱熹的结论是 X,你怎么看?请用{你的视角}评 1 段"
    )
```

**为什么不用 sub-agent 自己互查**:
- 防止 sub-agent 互相干扰,又回到 context 污染
- 主控中转 = 单点可控

**报告标注**:并行下 6 方向是主控推测,不是各司互评。

### 差异性自检修复动作（v3.1.2 P1 · WorkBuddy E 坑修正）

❌ **旧动作(无效)**:
- 相似度 > 70% → 报警 + 重跑差异最低的 1 司
- 问题:重跑孤立 context 大概率仍同结论,白烧第 4 倍 token

✅ **新动作(v3.1.2 修正)**:
1. 主控收齐后比对 3 份结论,若高度雷同(非仅开头措辞)
2. **优先查角色分工是否失效**:三诀是否在同一维审三遍、重叠无互补?
   - 若是 → 升级调整分工(**不重跑**,重跑孤立 context 大概率仍同结论)
3. 若确认维度单一(议题小、本就维度少)→ 接受雷同,标「低维度任务 · 三司独立但同结论」
4. 重跑降级为可选(不自动触发)
5. 报告标注「三司独立结论 · 但维度单一 · 接受雷同」

### 圆桌参与司：默认三司但可降级（v3.1.2 P1 · WorkBuddy F 坑）

- 圆桌默认三司全跑
- 但报告标注各司「边际贡献」(主控 P2 评估):
  - 「边际贡献高」= 该司补充了其他司未覆盖的维度
  - 「边际贡献低」= 该司与其他司高度重叠,价值有限
- 「边际贡献低」= 成本透明,下次类似任务可考虑降级为默认模式

### 假设穿透综合（v3.1.2 P1 · WorkBuddy 隔离补丁）

> 隔离买到"不被前司带偏"，但可能稀释"假设穿透的协同深度"——三处穿透散在三个孤立 context。

- 主控把三司各自戳破的隐藏前提 / 信念妄执汇总成 1 张清单（报告必填）
- 确保隔离下三处穿透不被散落丢失

### 落地四问归属（v3.1.2 P1 · WorkBuddy J 坑补充）

- 落地轴（用户 / 成本 / 风险 / 项目对齐）由**主控在 P4 整合时补填**，不派发给子 agent
- 三诀审「对不对 / 信不信 / 全不全」，落地轴为编排层附加
- 子 agent 不重复审也不漏审

### 异常信号按模式区分（v3.1.2 P2 · WorkBuddy I 坑）

| 异常信号 | 串行模式 | 并行模式 |

## 🎯 设计初衷（錡哥 9:15 原文 · v2.5 补入 · 必读）

### 錡哥原话 · 主控

> 「主控不是车间流水线，不是联络员，是**整个项目的核心大脑**，他需要**先深入分析理解任务需求**，根据任务需求，制定**详细的任务计划**，当前什么该做，什么不该做，应该先做什么，后做什么。**并且要实时跟进**，不是部署完任务就算了，要从任务开始跟进到任务结束，**时刻盯紧任务过程**。如果发现有异常，要根据最新的情况，**实时调整整个任务规划**，是整个任务的总规划，要**实时调整方向盘**，防止路线偏移。」

### 錡哥原话 · 会审

> 「会审不是车间流水线，不是你审完就交给我审，每人分别审一次，审完就结束。首先，需要把原本的流水线审计流程，根据第一性原理，**全部打散，拆解成最小可执行单元**，每个可执行单元，都是可用的模组。然后**根据任务实际需求，从可用的模组里挑选出合适的模组**（可重复选择，自由组合），**重新组装最合适的审计流程**。如果发现有异常，**整个审计流程需要重新设计，动态调整**。」

### 錡哥原话 · 三司

> 「三司是不仅仅是调用三个 skill 这么简单，这是**三个不同部门，三个不同专家**，在共同协作处理同一个事项，需要**互相配合、取长补短**，必要时，可以**互相讨论，互相印证**，甚至**开一次圆桌会议**。」

### 三句话连读

| 关键词 | 锥心 |
|------|------|
| 主控 | **核心大脑**（不是流水线）· **实时跟进到任务结束** · **防止路线偏移** |
| 会审 | **打散到最小单元** · **自由组合** · **异常时重设计** |
| 三司 | **三个部门协同** · **互相印证** · **必要时圆桌会议** |

#### 奥卡姆闸门（v4.1 整合 · 2026-09-03 · ponytail 极简理念）
> 奥卡姆剃刀「如无必要，勿增实体」；老子《道德经》「损之又损，以至于无为」——本闸门即取刀之处，动手前先砍一遍不必要。属技法层闸门，不进四诀名册、不披心法壳（§1 文化依据条款合规锚点，西方锚，与儒释道兵并列，不问出身）。

**位置锚点**：编排层「制定计划 → 执行跟进」写码转场。**不依赖破妄诀被调起**即可独立运行。

**skip-detection（必含，否则标红升级）**：输出须显含——
`奥卡姆闸门结果：第 X 问通过 / 不通过`

**与落地四问分工**：奥卡姆闸门查「必要性」（该不该写），落地四问查「可执行性」（写不写得出、靠不靠谱）。

**7 级阶梯（唯一权威源）**：详见 `powang-jue/references/ponytail-ladder.md`，主文件不载阶梯原文（防双源漂移）。

- **off 条件**：trivial 改动（<5 行 / 纯配置 / 纯文案）跳过；三司走「跳过模式」时不触发。
- **边界**：只管「写多少 / 该不该写」，不管「对不对」——方向判断仍归四诀（明辨/破妄/五行/知彼）。

#### 输出纪律（v4.3 新增 · 奥卡姆闸门 per-reply 工位 · 治「自加戏」）
> 同一把刀的**第三个工位**：阶段 2 管**动手**（写多少）→ 阶段 4 管**落地**（建议留几条）→ 本工位管**开口**（答什么、答到哪停）。思想锚：**Grice 合作原则 · 量的准则**（Grice 1975《Logic and Conversation》："Do not say more than is required"）——西方锚，可溯源，与 ponytail + 老子「损之又损」同刀共源，**不新增模块名**（§1 文化依据条款 + v4.2「同一把刀多工位」先例）。

**硬禁令（3 条 · 回答动作前必过）**：
1. **用户问了什么，答什么。**
2. **用户没问的，不主动说**——含「待建 / 建议 / 后续优化 / 反思问题 / 顺便一提」等扩展尾巴。
3. **答完 → 句号。**

**skip-detection（砍了才报，M=0 静默）**：M>0 时输出须显含——
`输出纪律：用户问 N 项 · 答 N 项 · 自加 M 项已砍`
- **M=0 时不输出本行**——闸门自身不得成为新的自加内容（治「为显示守闸门而自加一行」反模式，2026-09-07 会审 sanshi-20260907-002 破妄·空执裁定）。
- M>0 而未输出 → 标红升级。

**off 条件**：用户问「你怎么看 X」（开放问题）→ 必须给独立判断；用户显式说「顺便看 X」→ 放行 X；对比问题 → 不砍一半。

**层级边界（2026-09-07 会审外部视角裁定）**：三司会审是任务级编排，仅被调用时运行；**普通对话的自加戏不归本条管**——由用户级输出约定（`~/.workbuddy/MEMORY.md`）承载，本条为会审内引用。

### 🔄 自动更新协议（7 天间隔 · 资源平衡 · 8-15 錡哥拍板）

> **问题**：每次 skill 启用都查 GitHub = 浪费系统资源。
> **方案**：7 天间隔 + 本地时间戳闸门。能不查就不查。

**机制（6 步）**：
1. 每个诀目录下存 `.update-check.json`：`{"lastCheck": "ISO 8601 时间", "lastSha": "上次见到的 commit sha", "lastVersion": "vx.x"}`
2. skill 启用时先读本诀的 `.update-check.json` 的 `lastCheck`
3. `now - lastCheck >= 7 天` → 触发检测：拉本诀 raw 直链取版本号 + 调 GitHub commits API 取本诀 SKILL.md 最新 commit sha，二者任一与本地不符即判为有更新（**7 天内一律不联网**，节流优先于比对）
4. sha 不同 **或** 版本不同 = 有新版 → **仅打印提示，不自动覆盖本地文件** + 更新 `.update-check.json`（lastCheck + lastSha + lastVersion）
5. sha 相同 **且** 版本相同 = 无更新 → 仅更新 `lastCheck`
6. `now - lastCheck < 7 天` → 跳过检测，直接用本地版

**时间戳路径**：`~/.workbuddy/skills/<诀名>/.update-check.json`（每个诀独立一份）

**触发点**：skill 实际启用时（即被调用/加载进上下文时），**不是每次对话**。日常对话不触发检测。

**首装特例**：首次安装时 `.update-check.json` 不存在 → 当作"立即检测一次"，写入时间戳 + sha，之后走 7 天间隔。

**协议源**：本协议由三司会审主控定义，4 诀遵循（4 诀自描述块已指向三司会审编排入口，更新协议同源，不必在各诀重复全文）。
