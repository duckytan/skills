## 审查流程（6 步法 · 含第 0 步 Pre-Mortem）

### ⚡ 轻量模式 / 快速审查

如果审查对象明显简单（单文件审阅、配置检查、bug 复现），跳过事实收集和推荐行动，只做：
- 否定性对抗（质疑假设）
- 追问性对抗（验证结论）
- 一句话根因

**自动判断规则**：审查对象 < 3 个变量 或 < 5 条可分离事实 → 自动降级轻量模式。

### 第 0 步：Pre-Mortem（项目启动前必做 · critical）

> **借鉴**：Gary Klein 2007 HBR "Performing a Project Premortem" + Mitchell/Russo/Pennington 1989 Prospective Hindsight
> **作用**：在审查开始**前**想象"项目已经失败" → 倒推所有可能的失败原因

```
## Pre-Mortem 输出格式
**假设失败时点**：项目已上线 6 个月
**想象失败情境**：xxx 已彻底失败
**倒推失败原因**（5-10 条）：
  1. xxx
  2. xxx
  ...
**高风险信号**（标红·列入 critical 必查项）：
  - xxx
**已预防措施**：xxx
```

**为什么有效**：利用"prospective hindsight"认知现象，把未来视角变成当下分析，**风险识别率提升 30%**。

### 第 1 步：事实收集

> **🆕 8-3 知彼诀集成**："事实收集"能力已提取到知彼诀（`~/.agents/skills/zhibi-jue/` 知己·盘点方法）。明辨诀作为**纯法官**不再自行收集事实——**输入 = 调用方提供的「事实清单」+「验证结果」**（由知彼诀前置情报包或主控阶段 0 提供）。若调用方未提供事实清单 → 明辨诀拒绝审查（缺输入）→ 主控需先调知彼诀知己方法。法官不亲自取证，法官审证据。

列出所有已确认的客观事实（facts），每一条都必须有来源佐证：
- 日志原文 / 配置文件原文 / 工具输出 / 运行结果
- 标记每条事实的**确信度**（高/中/低）

### 第 2 步：否定性对抗（5 假设 + 5 追问）

对**每一个假说、推断、假设**执行否定性质问。

#### 5 种假设分类（先归类，再对抗）

| 类型 | 描述 | 追问方向 |
|------|------|---------|
| **Consensus** | 共识/大家公认 | "谁说的？为什么信？有没有反例？" |
| **Hidden** | 隐藏在语言/默认设置里 | "不写出来会怎样？假设合理吗？" |
| **Authority** | 因为权威信了 | "源头还成立吗？权威本身有没有错？" |
| **Temporal** | 过去对、假设现在还对 | "时点变了没？环境变了没？" |
| **Correlation** | 共存就当成因果 | "相关 = 因果？有没有第三变量？" |

#### 5 个否定问题

- "如果这个假设是错的，现象会是什么样？"
- "有没有其他解释能同时解释所有事实？"
- "有没有更简单的解释？"
- "这个结论隐含了什么前置条件？这个条件成立吗？"
- "如果把这个原因去掉，现象是否还存在？"

#### 3 档结论分类（v1.0 已有 · v2.0 保留）

| 标记 | 含义 | 处理 |
|------|------|------|
| ✅ **Survives** | 经受住所有对抗测试，可信 | 写入最终结论 |
| ⚠️ **Conditional** | 某些条件下成立，需标注条件 | 写入时附带前提 |
| ❌ **Fails** | 被否定证据击破，放弃 | 写入"已排除的假说" |

### 第 3 步：追问性对抗 + 绿黄红风险等级（v2.0 新加）

对**每一个看似成立的结论**追问：
- "这个结论有直接证据吗？还是推断出来的？"
- "证据链是否完整？有没有跳过的步骤？"
- "有没有考虑过时间线？先发生和晚发生的有因果关系吗？"
- "是不是把相关性和因果性搞混了？"
- "是不是看到相似时间戳就归类为同一原因？"
- "有没有更精确的说法？"

#### 绿黄红风险等级打分（v2.0 新加 · 与 3 档结论分类**共存**）

| 等级 | 颜色 | 含义 | 处理建议 |
|------|------|------|---------|
| 🟢 | **绿** | 低风险 | 可继续推进 |
| 🟡 | **黄** | 中风险 | 建议增加防御措施后再推进 |
| 🔴 | **红** | 高风险 | **停止推进**，必须先解决 |

**与 3 档结论分类的关系**：
- 3 档分类（Survives/Conditional/Fails）= **结论可信度**（逻辑层）
- 绿黄红 = **风险严重度**（业务层）
- 两者可独立评估：一个 Conditional 结论可能是 🟢 低风险（条件可控）；一个 Survives 结论可能是 🔴 高风险（幸存但仍危险）

### 第 3.5 步：反方视角

对当前最确信的结论，自问：
- "如果我是另一个 AI，看到同样的事实，会得出什么不同结论？"
- "我是不是选择性关注了支持我的证据？有没有被我忽略的反例？"
- "这个结论太漂亮了，是不是太漂亮了？"

#### 6.5 子步骤：系统环境核验（v3.0.2 必走 · 7-16 P0 触发）

> **背景**：7-16 磁盘方案 v1.0 改 `ulimit -c 0` 禁用 core dump，但系统装了 ABRT（Automatic Bug Reporting Tool），内核把 core dump pipe 给 `/usr/libexec/abrt-hook-ccpp`，**完全绕过 ulimit**——方案 v1.0 0% 生效。
> **核心警示**：**改系统配置 ≠ 自动生效**——必有"系统服务依赖"在底层接管。审方案 = 审方案 + 审系统环境。

**必查 5 类系统服务拦截器**：

```bash
# 1. core dump 接管者（最常见盲点）
cat /proc/sys/kernel/core_pattern    # 若含 | 开头 = pipe 给其他服务
ls /etc/abrt/ 2>/dev/null            # Red Hat 系 ABRT 配置
cat /etc/systemd/coredump.conf 2>/dev/null  # systemd-coredump 配置

# 2. 审计服务（拦截文件访问/系统调用）
systemctl status auditd --no-pager
auditctl -l 2>/dev/null

# 3. 自动 bug 报告（Ubuntu apport 等）
ls /etc/apport/ 2>/dev/null

# 4. cron 拦截（systemd-timer 覆盖 cron？）
systemctl list-timers --no-pager | head

# 5. 日志/资源拦截（logrotate/journald 配额）
journalctl --verify 2>&1 | head -3
cat /etc/systemd/journald.conf 2>/dev/null | grep -v '^#'
```

**修改后必验证（v3.0.2 加）**：

```bash
# 不只是看配置改了 — 要看"实际生效"
prlimit | grep CORE          # 实际进程 limit
ulimit -c                    # 当前 shell
# 真触发一次测试（如 yes | python3 -c "import ctypes; ctypes.string_at(0)"）
```

## 质量标准

1. **每个假设可证伪** — "如果 X 错，会是 Y 现象"
2. **每个结论有证据** — "X 说"必须指明谁说、什么时候、为什么信
3. **至少 1 个非显然洞察** — 如果只是确认常识，再深挖
4. **反方不是为反而反** — 既然常识是真的就直说
5. **不确定 ≠ 假** — "没法证明真的"和"是假的"是两件事
6. **承认认知边界** — 哪些问题工具/视野够不到，明确说出

## 规则

1. **不急着动手** — 审查阶段不产生任何写操作
2. **不在证据不足时下结论** — 标记为"待验证"
3. **承认错误推断** — 明确说"我之前的推断错了"
4. **输出精简** — 只报需要使用者知道的内容
5. **先否定再肯定** — 默认假设"现在的一切推断可能都错了"
