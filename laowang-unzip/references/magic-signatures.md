# 魔数速查与文件头判定（magic-signatures）

> 供 `pipeline/core/header.py` 实现用。判据全部来自真实批次实测（v1 16 坑 + v2.1 设计文档）。
> 核心认知：**伪装包的签名没有一个在 offset 0**——只查文件头会全部漏掉。

## 1. 魔数表

| 真实类型 | 签名（十六进制） | offset | 常见伪装后缀 | 误报率 |
|---|---|---|---|---|
| 7-Zip | `37 7A BC AF 27 1C` | 0 | .png .mp4 .pdf .txt .jpg | **零误报，命中即真** |
| RAR4 | `52 61 72 21 1A 07 00` | 0 | .rar | **零误报** |
| RAR5 | `52 61 72 21 1A 07 01 00` | 0 | .rar | **零误报** |
| ZIP | `50 4B 03 04` (PK..) | 0 | .apk(合法不动) .zi .zipSC .ziiip .删7z | **高，需结构校验**（见 §2） |
| TAR | `75 73 74 61 72` (ustar) | 257 | .tar | 低 |
| MP4/MOV | `66 74 79 70` (ftyp) | 4 | .mp4 | ——**看似视频 ≠ 真视频**（见 §4） |
| PNG | `89 50 4E 47` | 0 | — | 低 |
| JPEG | `FF D8 FF` | 0 | — | 低 |
| EXE | `4D 5A` (MZ) | 0 | .exe | 低 |
| GZIP | `1F 8B` | 0 | — | **仅 3 字节，视频里随机命中概率极高 → 一律当噪声** |
| BZIP2 | `42 5A 68` (BZh) | 0 | — | 同上，噪声 |

## 2. ZIP 命中必须做结构校验

视频二进制里会随机出现 PK 头，裸命中不算数。校验 local file header：

- method 合法（0–19 或 93–99；`0x0063`=99 即 WinZip AES 加密）
- 文件名长度 `fnlen` ∈ [1, 1024]
- `csize`/`usize` 不超过 filesize；**Zip64 用 `0xFFFFFFFF` 当哨兵**，真实大小在扩展字段——
  不要因为 csize > filesize 误判为噪声而跳过。

## 3. 篡改 magic：UA→PK（实测 `W-我的妹妹不可爱.dzi删除` 698 MB）

- 现象：文件头 `55 41 03 04 33 00 09 08 63 00 ...`——`PK`(50 4B) 被改成 `UA`(55 41)，
  后面紧跟正常 zip local file header 字段，**文件名可读**。method=99 = WinZip AES 加密。
- 识别口诀：头 4 字节不是任何已知 magic，但**偏移 4~30 附近能读出可读文件名/路径** → 八成是 magic 被改了几个字节。
- 修法：把全文所有 `55 41 XX XX` 批量替换回 `50 4B XX XX`，覆盖五种结构：
  `03 04`(LFH) / `01 02`(CD) / `05 06`(EOCD) / `06 06`(EOCD64) / `07 08`(DD)。
  写成新 `.zip`（origin=`MAGIC_PATCHED`，**显式入队**）。698 MB 里误伤概率 <0.05 次，可接受。
  修完用 `7z t` 验证；**仍需密码**（走密码流程，不是修完就免密）。
- 产物落**源包同目录**（不在 out_dir 下）——这就是 v2.1 §3.3 第 8b 步要求四类修复产物显式入队的原因。

## 4. 头伪装与 carve（老王论坛主力手法）

- 现象：文件 offset 4 是**合法** `ftyp` 盒（看起来就是视频），但其后嵌着真 7z/zip 签名，
  真签名位置从 offset 36 到几十 MB 不等。系统显示视频图标。
- 案例：`大学新生方法论.mp4`(144MB) = 假头 36 字节 + 加密 7z(opkk052) + 内层加密 7z + 真 mp4；
  `事考课程.mp4`(140MB) = 假头约 65 MB + 真 zip(PK) + 内层 7z + 国考资料.txt。
- **规则**：对"看似视频/图片"的文件也必须做**整文件任意偏移签名扫描**；命中即 carve——
  从签名 offset 割到 EOF 存成 `<名>.zip/.7z`（origin=`CARVED`，显式入队）。
- 割出的包在删除源 mp4 前必须用 `7z l` 复核 carved 兄弟包状态（删除 check#10）：
  - `VALID`（能列条目）→ 源 mp4 是冗余，可删；
  - `ENCRYPTED`（提示 `Enter password`）→ carved 包有效但缺密码，**源 mp4 + carved 包都保留**；
  - `INVALID`/not archive（carve 切错位置）→ 源 mp4 **保留**，坏 carved 包可当垃圾清；
  - 整文件只扫到 gzip 噪声、无任何真签名 → 可能是真视频被误判，**不要 carve，保留**。

## 5. 7z 32 字节签名头解析（判"加密头 vs 损坏"与分卷的唯一可靠手段）

```
sig(6) + ver(2) + startCRC(4) + NextHeaderOffset(8, LE @12) + NextHeaderSize(8, LE @20) + NextHeaderCRC(4)
归档声明结束位置 = 32 + NextHeaderOffset + NextHeaderSize
```

- `声明结束位置 <= 文件大小` 且 magic 合法 → **结构完好**。此时 7z 报
  `Cannot open the file as archive` = **`-mhe` 加密头（密码问题）**，不是损坏。
- `声明结束位置 > 文件大小` → 真截断/损坏（`ARCHIVE_CORRUPT`）。
- 分卷判据：`01` 卷头合法但 `声明结束位置 > 01 实际大小` → 它是分卷卷 1，缺的就是续卷
  （实测 5 组全部精确到字节吻合：400.0 + 287.5 = 声明 687.5 MB）。
- 两个"扫描不到签名"的分卷陷阱：
  - **7z 分卷被改名成 01/02**：`01` 有合法 7z 头、`02` 头部随机字节被判 UNKNOWN。
    两者体积常为整 MB。判 `声明结束位置 > 01 大小` 即按**拼接**处理（二进制 copy 合卷），
    **别判"截断需重下"**。
  - **只缺首卷且首卷名被加"删"字**（`神墓.part1.rar删`）：续卷全在，只是首卷打不开。
    `os.rename(src, src[:-1])` 去掉末尾字符再试，7z 自动续卷。

## 6. 轻 vs 重两级判定（性能红线）

| 级别 | 函数 | 读多少 | 用途 |
|---|---|---|---|
| 轻量（前置） | `header.probe_magic_only()` | 前 32 KB，单次 < 1 ms | 主循环第 3 步，仅为去重前置定 `is_archive` |
| 完整 | `header.analyze()` | 整文件扫签名 + 7z 头解析 | 主循环第 5 步，去重未命中之后才做 |

禁止把完整分析前移到去重之前：整文件扫描对 46 GB 批次意味着几十 GB 额外顺序读，
而且去重命中的包根本不需要它（成本差 5 个数量级，命中时全浪费）。

## 7. 无害碎片（不是包）

- 文件**末尾**约 300 字节的伪 zip 碎片 = 已解主包尾部的随机 PK 命中，无害，不作为独立包。
- 文件末尾"RAR 尾挂"若 7z 报 `Cannot open the file as archive` 且末尾实为 mp4 `mdat` 数据 → 巧合字节，非真 RAR。
